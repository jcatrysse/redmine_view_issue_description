Major, lib/redmine_view_issue_description/patches/issue_patch.rb:243
Only direct user memberships are considered when building watched_clauses; group-based project memberships and non-member roles on public projects are ignored. As a result, users who have :view_watched_issues via a group membership (or via the Non member role on a public project) won’t get the watched OR-condition added to Issue.visible_condition, so watched issues won’t appear in lists/gantt/search/activity even though the user can open them (and should see watched issues when the role allows it).
Concrete failure: Private project P has Group G as a member with a role that grants :view_watched_issues (all trackers). User U is only in group G (no direct membership), and U watches Issue I in P. Visiting /projects/p/issues or /issues.json as U does not list I (base_condition excludes it and watched_clauses is empty), while a direct GET /issues/:id can be allowed elsewhere by allowed_to? checks including group roles.
Fix: Include group memberships and (for public projects) the Non member role when building watched_clauses. For example:
- Preload user.groups and their memberships: ActiveRecord::Associations::Preloader.new(records: [user], associations: { memberships: [:roles, {project: :enabled_modules}], groups: { memberships: [:roles, { project: :enabled_modules }] } }).call
- Merge memberships = user.memberships.to_a + user.groups.flat_map(&:memberships)
- Optionally, for public projects where Role.non_member.allowed_to?(:view_watched_issues), add a synthetic clause for those projects (respecting tracker scoping) limited by scoped_project_ids if present. Alternatively, replace roles usage with roles_for_project(project) per project id derived from memberships (user + groups) to cover both direct and group roles without scanning all projects.

Resolution: not changed. Redmine gives every user of a group its own inherited member row (Group#user_added), so user.memberships, read before and after 10a6f14 alike, includes group roles; test 'a role given through a group counts' in test/unit/visible_condition_cost_test.rb (d491240) proves it. The Non member role on a public project was never part of the watched clause (same as before this change); behaviour is kept identical as the task requires.

Minor, lib/redmine_view_issue_description/watched_clause_cache.rb:26-30
The cache is not invalidated when group membership changes (GroupsUser). The code claims “Any change … clears it at once,” but adding/removing a user to/from a group (which affects effective project roles and thus watched_clauses) does not trigger a clear, causing stale conditions within the same request that changes group membership and then evaluates visibility.
Concrete failure: Within a single request (e.g., a controller action or job) that adds a GroupsUser linking U to G, then renders an issues list for U, the first call to Issue.visible_condition(U) is computed before the change and is reused (via WatchedClauseCache.fetch), omitting projects now gained via G.
Fix: Add cache invalidation hooks for GroupsUser (and optionally Group):
[GroupsUser, Group].each do |model|
  model.after_save { RedmineViewIssueDescription::WatchedClauseCache.clear }
  model.after_destroy { RedmineViewIssueDescription::WatchedClauseCache.clear }
end

Resolution: not applicable. Adding a user to a group makes core create member and member_role rows for that user, whose after_save clears the cache; the same test (d491240) adds the user to the group in the same request and sees the new clause.

Concrete failure: In a fresh Rails runner/process that hasn’t loaded Set yet, invoking the search path that hits Issue.search_with_vid (e.g., rails runner 'User.current=User.find(2); Issue.search("foo", User.current)') raises NoMethodError: undefined method `to_set' for Array.
Fix: Add require 'set' at the top of this file (or replace to_set with a Set constructed explicitly after requiring 'set').

Resolution: not applicable. Redmine 7 requires Ruby >= 3.2, where Set and Enumerable#to_set are available without require (checked: `ruby -e 'p [1,2].to_set'` on 3.3.6); Rails loads set as well.
