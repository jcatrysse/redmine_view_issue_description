Major, lib/redmine_view_issue_description/patches/issue_query_patch.rb:13
Per-issue permission check in IssueQueryPatch introduces N+1 queries on lists
- Problem: issues.each { |issue| issue.vid_hide_description! unless issue.detail_access_granted?(user) } calls Issue#detail_access_granted? for every row. That method consults assigned_to and watcher status. Unless preloaded, each access will trigger separate queries (assigned_to association fetch; watched_by?/watcher checks), causing N+1 (or worse) queries on issue lists (HTML, CSV, Atom, API index), especially visible with larger limits (e.g., 100).
- Failure scenario: On a project with 100 visible issues, a user without view_issue_description opens the issues list with the description column. Logs show ~100 SELECTs to load assigned_to principals and ~100 SELECTs/EXISTS on watchers (one per issue), slowing the page/API response significantly. This regression is new because previously the plugin hid the whole column without per-row checks.
- Fix: Preload the associations used by the check before iterating, and rely on Redmine’s watched_by? fast path on preloaded watcher_users. For example:
  def issues(options = {})
    list = super
    user = User.current
    return list if user.admin? || list.blank?
    ActiveRecord::Associations::Preloader.new.preload(list, [:assigned_to, :watcher_users])
    list.each do |issue|
      issue.vid_hide_description! unless issue.detail_access_granted?(user)
    end
    list
  end
If watcher_access_granted? uses a different check than watched_by?, adjust preloading accordingly (e.g., preload :watchers if it inspects Watcher records directly).
