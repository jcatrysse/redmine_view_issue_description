Major, lib/redmine_view_issue_description/patches/mailer_patch.rb:1 (missing coverage of Mailer.attachments_added)
- Problem: The plugin filters description, notes, and attachment names for issue_add and issue_edit mails only. Redmine also sends “attachments added” notifications (Mailer.attachments_added) when files are added to an issue (via AttachmentsController). Those mails include the filenames and often the files themselves. For recipients who may not open the issue (no view_issue_description and not otherwise allowed), this leaks attachment names (and content if attachments are included) despite the round 3 decision.
- Failure scenario: A user without view_issue_description is a watcher on an issue. Another user adds files to the issue (with no note, or even via AttachmentsController). Redmine sends an “Attachments added” mail to watchers. Because attachments_added is not wrapped by vid_restricted_for, the mail to the restricted watcher contains the filenames (and may include the actual files), bypassing the plugin’s new restrictions.
- Fix: Patch Mailer.attachments_added similarly to issue_add/issue_edit:
  - If added_to is an Issue and !added_to.detail_access_granted?(recipient), temporarily hide attachments on the issue (vid_hide_attachments!) while rendering the mail, and strip any attachment details from the per-attachment lines (either by skipping attachments entirely for that recipient or by filtering the rendered details list).
  - Concretely, in MailerPatch:
    - Define attachments_added(user, attachments, added_to) { vid_restricted_for(user, added_to) { super } } (ensure it matches the core signature in 7.0).
    - If the core implementation iterates the attachments list directly (not via added_to.attachments), set attachments = [] for that recipient before yielding, or filter the rendered list.
  - Add tests that fail on the current code: a recipient without detail access receives an attachments_added mail that must not contain filenames and must not include the files.

Resolution: not applicable, no change. In Redmine 7.0-stable-GEOxyz `Mailer.deliver_attachments_added` is only called from FilesController#create and DocumentsController#add_attachment, and `Mailer#attachments_added` handles only Project, Version and Document containers (app/models/mailer.rb 175-188). Files added to an issue go through the issue update, i.e. the issue_edit mail, which round 3 already covers (a922545, mailer_notes_attachments_test.rb).

Minor, lib/redmine_view_issue_description/patches/journal_patch.rb:33
- Problem: find_events maps each returned journal to its issue via events.map(&:issue). If the activity scope does not eager-load issue (e.g., due to future core changes or another plugin altering the scope), this introduces an N+1 query on every Journal event when rendering activity pages/feeds.
- Failure scenario: A project with many journal events (e.g., 200 updates) on the activity page. If Journal.find_events isn’t including :issue, find_events will fire 200 extra queries to resolve journal.issue, adding noticeable latency.
- Fix: Avoid dereferencing journal.issue. Compute openable using IDs:
  - Collect ids = events.map(&:journalized_id).uniq
  - Fetch issues once Issue.where(id: ids) as needed inside Issue.vid_openable_ids (or introduce Issue.vid_openable_ids_by_ids(ids, user)) so there’s at most one query. Then mark journals by checking membership in the returned id set.

Resolution: no change. Core's activity scope for Journal preloads `{:issue => :project}, {:issue => :tracker}` (app/models/journal.rb 52-61), so `events.map(&:issue)` reads loaded records; Issue.vid_openable_ids then preloads what the check needs in one query each. Should a plugin drop that preload, the cost is one query per journal on that page, not wrong output.
